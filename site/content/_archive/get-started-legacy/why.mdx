Modern backends accumulate many independently adopted systems: routers, queues, crons, websockets, caches, vaults, mailers, AI wrappers, and observability agents.

Each tool brings its own configuration format, lifecycle semantics, error taxonomy, and operational dashboard.

<Callout title="A note on the count">
  'Forty' is a representative illustration of the number of backend concerns developers commonly
  assemble across modern stacks, not a literal census.
</Callout>

```text
many systems → many seams → many contracts → many mental models
```

## The Seams You Own

Every backend works on day one. The real operational tax arrives later in the seams between systems:

- **Cache that lies:** You update a database record, but forget to invalidate the cache key in another service.
- **Secret that fails at 2am:** Deploy boots fine, but the first charge fails because an environment variable was missing.
- **Permission checks in the wrong place:** Auth logic is scattered across handlers instead of verified at the trigger.
- **The dashboard that doesn't know you:** Observability tools learn routes from traffic samples instead of the compiled model.

## The Insight: One Programming Model

These operational concerns do not need to become separate programming concepts. They collapse into one closed set:

```text
Many backend concerns → One programming model
```

> **One law. Eight elements. One contract.**

## Wrong vs. Right Mental Model

Understanding OKEngine begins by rejecting the conventional feature-pile model:

| ❌ Wrong Mental Model (Feature Bundle) | ✅ OKEngine Model (Unified Primitives) |
| -------------------------------------- | -------------------------------------- |
| Router + Queue + Cron + Auth + ORM     | `on(Trigger) → Flow` (One species)     |
| Separate mental model per tool         | Eight closed semantic elements         |
| Ad-hoc side effects everywhere         | Single door to the world: `fx`         |
| Hand-maintained glue & OpenAPI         | Compiled Manifest contract             |
| Unchecked runtime drift                | Derived, inspectable surfaces          |

The difference is not how many features OKEngine has. It is how few concepts you need to understand.

## See the Model Compose

OKEngine does not add new subsystems when new architectural requirements emerge. The eight closed primitives compose naturally:

- **Realtime:** `Store + Gate + Signal + Flow → Live Query` (Global CDC + RLS re-check + SSE).
- **Security:** `Gate + Store/RLS + Tenant + fx → Secure execution` (Unified user, operator, and agent boundaries).
- **Agents:** `AI + Gate + Flow → Agent-accessible backend` (Exposing Flows as MCP tools).
- **Operations:** `Manifest + Effects + Runs → Inspectable backend` (Wide-event telemetry and live graphs).

<Callout title="Zero Subsystem Sprawl">
  None of these capabilities required a ninth primitive. New infrastructure arrives as a driver for
  an existing element.
</Callout>
