Jobs trigger Flows automatically according to wall-clock time, recurring intervals, or named cron expressions.

## What it is

Rather than spinning up external daemons or separate background runners, recurring tasks are declared directly alongside other Flows by referencing named Clock declarations.

```typescript
import { on, flow, clock } from "okengine";

export const nightlyDigestClock = clock("digest.nightly", {
  cron: "0 0 * * *",
  timezone: "Asia/Riyadh",
});

export const nightlyDigest = on(
  nightlyDigestClock,
  flow("digest.nightly", {
    do: async (_, fx) => {
      // Runs every night at midnight Riyadh time
    },
  }),
);
```

## Smallest Example

<Steps>

<Step>
### Create a recurring flow

```typescript title="src/flows/metrics/cleanup.ts"
import { on, flow, clock } from "okengine";

export const cleanupClock = clock("metrics.cleanup", { every: "1h" });

export const cleanupMetrics = on(
  cleanupClock,
  flow("metrics.cleanup", {
    do: async (_, fx) => {
      const oneWeekAgo = new Date(fx.clock.now() - 7 * 86400000);
      await fx.store(db).delete(metricLogs).where(lt(metricLogs.timestamp, oneWeekAgo));
    },
  }),
);
```

</Step>

<Step>
### Observe in Console

The runner registers the schedule at startup. In multi-instance deployments, leader election guarantees only one worker executes per tick.

</Step>

</Steps>

## Execution Mechanics

1. **Leader Lock**: In distributed deployments with Postgres or Redis, a short leader lock prevents multiple pods from firing the same job.
2. **Deterministic Time**: Accessing `fx.clock.now()` returns the exact scheduled tick time, making runs reproducible.
3. **No Catch-up Storms**: If a worker is offline for 3 hours, it executes only the single latest tick upon boot rather than bursting past missed runs.
